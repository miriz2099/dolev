# הסבר מקיף על הבדיקות האוטומטיות בצד השרת (Backend / Functions)
## פרויקט גמר: מערכת "דולב" (Dolev)

מסמך זה מרכז ומסביר בצורה מפורטת את מערך הבדיקות האוטומטיות שהוקם בצד השרת של המערכת (`functions/`), את המטרות ההנדסיות והקליניות של כל בדיקה, ואת אופן הרצתן.

---

## 📌 1. מטרת הבדיקות
מערכת "דולב" מנהלת מידע רפואי ואישי רגיש (תיקי אבחון פסיכודידקטי, שאלונים התפתחותיים, פרטי הורים וילדים) ומשלבת מודל בינה מלאכותית (Gemini) לניסוח קליני.
הבדיקות האוטומטיות מוודאות שלושה עמודי תווך קריטיים:
1. **פרטיות ואבטחת מידע (HIPAA & Privacy):** הבטחה ששום פרט מזהה של ילד או הורה לא נחשף למודל ה-AI.
2. **הגנת סייבר וסניטיזציה (Cyber & Injection Defense):** סינון תכנים זדוניים (XSS) תוך שמירה על שלמות חתימות דיגיטליות.
3. **בקרת גישה והרשאות (Authentication & RBAC):** וידוא שאף משתמש לא יכול לחרוג מהרשאותיו (למשל הורה שמנסה לגשת לממשק אדמין).

## 🚀 2. כיצד מריצים את הבדיקות?
מטרמינל הפרויקט (VS Code / PowerShell):
```powershell
npm --prefix functions test
```
או ישירות מתוך תיקיית `functions`:
```bash
npm test
```

כל הבדיקות רצות באמצעות **Jest** בסביבה מבודדת בזיכרון (In-Memory Mocks) ללא תלות ברשת וללא חיוב ב-Firebase.

## 🔍 3. פירוט סוויטות הבדיקות

### 🟢 סוויטה 1: התממת נתונים ואבטחת פרטיות ב-AI
**קובץ בדיקה:** `functions/tests/unit/deidentify.test.js`  
**קובץ קוד נבדק:** `functions/services/ai/deidentify.js`

השירות אחראי להסיר פרטים מזהים מהטקסט של המאבחנת לפני שליחתו ל-Google Gemini, ולהחזיר אותם לאחר קבלת הפלט המנוסח.

* **מה נבדק בפועל?**
  1. **מיפוי ישויות מושכל (`buildEntityMap`):**
     * וידוא ששמות הילד, שמות ההורים, ת.ז, מספרי טלפון ומיילים נאספים ומומרים ל-Tokens ייעודיים (כגון `[שם_הנבחן]`, `[ת.ז]`, `[טלפון]`).
     * בדיקת סינון: שדות ריקים או קצרים מדי (פחות מ-2 תווים) מסוננים כדי למנוע החלפות שגויות.
  2. **מניעת התנגשויות תת-מחרוזת (Substring Collision):**
     * הבדיקה מוודאת שהשמות ממוינים לפי אורך בסדר יורד. לדוגמה: אם שם האב הוא "דניאל" ושם הילד הוא "דן", המערכת תסווה קודם את "דניאל", כדי שהשם "דן" לא יחתוך את "דניאל" ויהרוס את המילה.
  3. **הסוואה בפועל (`redact`):**
     * החלפת כל הפרטים הידועים בטקסט הקליני ב-Tokens גנריים.
  4. **רשת ביטחון מבוססת Regex (Fallback Protection):**
     * בדיקה המוודאת שגם אם המאבחנת הקלידה ידנית בטקסט החופשי תעודת זהות בת 9 ספרות, טלפון ישראלי או כתובת מייל שלא הופיעו ברישומי הילד – רשת הביטחון תזהה ותסווה אותם מיד.
  5. **שחזור מושלם (`restore`):**
     * וידוא שלאחר קבלת הפסקה המנוסחת מה-AI, המערכת מחזירה את השמות והפרטים המקוריים במדויק למקומם.

### 🟢 סוויטה 2: הגנת XSS וסניטיזציה של קלט
**קובץ בדיקה:** `functions/tests/unit/sanitize.test.js`  
**קובץ קוד נבדק:** `functions/middleware/sanitize.middleware.js`

ה-Middleware מגן על שרתי המערכת מפני התקפות XSS (Cross-Site Scripting) והזרקת תגיות זדוניות דרך טפסים ושאלונים.

* **מה נבדק בפועל?**
  1. **סינון תגיות HTML (`stripTags`):**
     * וידוא שתגיות כמו `<script>` מומרות ל-Entities בטוחים (`&lt;script&gt;`) כדי שלא ירוצו בדפדפן.
  2. **הסרת פרוטוקולי JavaScript והאזנות לאירועים:**
     * וידוא מחיקה של מחרוזות מסוכנות כמו `javascript:alert(1)` ומאזיני אירועים כמו `onclick=`, `onerror=`.
  3. **שימור חתימות דיגיטליות (Base64) – מקרה קצה קריטי:**
     * הורים חותמים על טפסי הסכמה ברכיב `SignatureInput.jsx`, והחתימה נשלחת כמחרוזת תמונה ב-Base64.
     * הבדיקה מוודאת באופן חד-משמעי שתמונות חתימה תקניות **אינן משובשות או נחתכות** על ידי מנגנון הניקוי.
  4. **ניקוי רקורסיבי בגוף הבקשה (`sanitizeBody`):**
     * וידוא שהניקוי מבוצע לעומק על כל רמות האובייקטים והמערכים ב-JSON שנשלח ב-Body, בעוד ערכים מספריים ובוליאניים נשארים תקינים.

### 🟢 סוויטה 3: אימות זהות ובקרת הרשאות (Auth & RBAC)
**קובץ בדיקה:** `functions/tests/unit/auth.middleware.test.js`  
**קובץ קוד נבדק:** `functions/middleware/auth.middleware.js`

ה-Middleware מגן על נתיבי ה-API ומוודא שרק משתמשים מורשים יכולים לבצע פעולות, תוך הפרדה בין הורים, מטפלים ומנהלים.

* **מה נבדק בפועל?**
  1. **אימות טוקן (`verifyToken`):**
     * בקשה שנשלחת ללא Header של Authorization – נחסמת מיד עם סטטוס `401 Unauthorized`.
     * Header שלא מתחיל ב-`Bearer ` – נחסם עם `401`.
     * טוקן שפג תוקפו או אינו תקין – נחסם עם `401`.
     * טוקן תקני – עובר אימות בהצלחה, פרטי המשתמש מושמים ב-`req.user`, והבקשה ממשיכה לפונקציה הבאה (`next()`).
  2. **בקרת הרשאות מנהל (`verifyAdmin`):**
     * מניעת Privilege Escalation: משתמש מחובר שתפקידו אינו אדמין (למשל תפקיד `patient` או `therapist`) המנסה לבצע פעולת ניהול – נחסם מיד עם סטטוס `403 Forbidden` והודעה "Access denied. Admins only.".
     * משתמש בעל תפקיד `admin` מאומת בדאטהבייס ומקבל אישור גישה.
